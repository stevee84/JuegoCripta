Guía completa del proyecto CRIPTA (roguelike de mazmorra en Python 3.11+). Cubre estructuras de datos, componentes de cada integrante y flujo de datos del sistema.

1. Visión general del proyecto

CRIPTA es un juego roguelike de mazmorra por turnos. El jugador explora una cripta generada por el servidor, combate enemigos, recoge objetos, esquiva trampas y busca la salida. Los datos de la cripta vienen de un API REST con presupuesto limitado de solicitudes.

2. Estructuras de datos del proyecto

TablaHash — estructuras/tabla_hash.py (Steve)

Tabla hash con encadenamiento (chaining). Internamente es una lista de listas (buckets). Cada bucket almacena tuplas (clave, valor).

  • Capacidad inicial: 17 (número primo para mejor distribución)
  • Función hash: hash(clave) % capacidad
  • Colisiones: se agregan a la lista del bucket (encadenamiento)
  • Rehashing: cuando factor de carga > 0.75, duplica capacidad y reinserta todo
  • Complejidad: O(1) amortizado para insertar/obtener/eliminar
  • Quién la usa: Sofía, para la agenda de eventos y búsqueda de salas en el mapa
  • NO se usa en la caché (restricción explícita del profesor)

ListaDoble — estructuras/lista_doble.py (Joshua)

Lista doblemente enlazada con nodos que tienen .valor, .siguiente, .anterior.

  • Clase NodoDoble: contiene el valor y punteros bidireccionales
  • Clase ListaDobleImpl: mantiene .primero, .ultimo, .cantidad
  • Operaciones clave:
    • insertar(valor) → retorna el NodoDoble creado, O(1)
    • quitar_nodo(nodo) → desconecta un nodo específico, O(1)
    • mover_al_frente(nodo) → mueve un nodo existente al inicio, O(1)
    • reinsertar_nodo(nodo, anterior, siguiente) → reconecta un nodo entre dos vecinos, O(1)
  • Quién la usa: Caché LRU (Steve), Inventario (Joshua), Historial reversible (Joshua/Sofía)

Arreglo ordenado — dentro de logica/cache_catalogo.py (Steve)

Lista de tuplas (clave, NodoDoble) mantenida en orden alfabético por clave.

  • Búsqueda: binaria con bisect manual, O(log n)
  • Inserción/eliminación: O(n) por desplazamiento de elementos
  • Justificación: con capacidad máxima de 25 elementos, log₂(25) ≈ 5 comparaciones. La diferencia con O(1) de una tabla hash es irrelevante; el cuello de botella real es la red (~400ms por request)

MontículoMínimo — estructuras/monticulo_minimo.py (Sofía)

Min-heap basado en array para la agenda de eventos.

  • Propiedad: el evento con menor tiempo siempre está en la raíz
  • Operaciones: insertar O(log n), extraer mínimo O(log n)
  • Quién la usa: AgendaEventos para extraer el próximo evento a procesar

ÍndicesOrdenados (AVL) — dentro de logica/agenda_eventos.py (Sofía)

Tres árboles AVL para búsqueda rápida en la agenda:

  1. Por ID de evento → cancelar un evento específico en O(log n)
  2. Por prioridad (tiempo, secuencia) → orden determinista
  3. Por destinatario → buscar eventos de un actor específico en O(log n)

Estos índices permiten cancelar y reprogramar eventos sin recorrer todo el montículo.

3. Integrante 2 (Steve) — Datos y Persistencia

Todo lo que entra y sale del programa: red, archivos, caché, guardado.

ClienteAPI — datos/cliente_api.py

Adaptador HTTP que implementa el contrato FuenteDatos. Genera un X-Cripta-Client-Id (UUID) al inicio de sesión.

7 endpoints:

MétodoRutaPropósito
listar_criptas()GET /criptasLista las criptas disponibles
obtener_generales(id)GET /criptas/{id}Metadatos: sala inicial, salida, llave
obtener_pagina(id, n)GET /criptas/{id}/salas?pagina=nEsqueleto de salas (paginado)
obtener_contenido(id, salas)GET /criptas/{id}/contenido?salas=1,2,3Enemigos, objetos, trampas
obtener_catalogo(ids)GET /catalogo?ids=x,y,zFichas del catálogo (stats de ítems)
obtener_version_cripta(id)GET /criptas/{id}/versionVersión de una cripta
obtener_version_catalogo()GET /catalogo/versionVersión del catálogo

Manejo de errores: 200 → parsear JSON. 429 → esperar reintentar_en (tope 30s), reintentar hasta 3 veces. Timeout/ConnectionError → reintentar hasta 3 veces. Otro código → lanzar CriptaAPIError. El juego nunca crashea por un error de red.

FuenteOffline — datos/fuente_offline.py

Mismo contrato FuenteDatos pero lee archivos JSON locales en vez de HTTP. Se activa con --offline. Cero solicitudes, cero presupuesto.

Caché LRU — logica/cache_catalogo.py

Política Least Recently Used sin TablaHash. Combina dos estructuras:

  1. Arreglo ordenado de tuplas (ficha_id, NodoDoble): búsqueda binaria O(log n)
  2. ListaDoble (de Joshua): orden de uso. Frente = más reciente, cola = más viejo

Operaciones:

  • obtener(ficha_id): bisect en arreglo → encuentra NodoDoble → mover al frente → retornar ficha
  • insertar(ficha_id, ficha): si lleno → evictar el más viejo no fijado → crear EntradaCatalogo → insertar en lista → insertar en arreglo manteniendo orden
  • fijar(ficha_id): protege una ficha de ser desalojada (en uso activo)
  • liberar_referencia(ficha_id): quita la protección

EntradaCatalogo: wrapper liviano con __slots__ = ("ficha_id", "ficha", "fijada") que vive dentro de cada NodoDoble.valor.

RepositorioCatalogo — service/repositorio_catalogo.py

Tres niveles de búsqueda: memoria → disco → red.

  1. Caché LRU (memoria): si la ficha está en caché, retornar (~0ms)
  2. AlmacenPersistente (disco): si está en disco y versión vigente, cargar al caché (~5ms)
  3. ClienteAPI (red): pedir al servidor, guardar en disco + caché (~400ms)

resolver_lote(ids) filtra los que ya tiene y pide solo los faltantes en un request. Efecto acumulativo: quinta partida gasta mínimo presupuesto.

AlmacenPersistente — datos/almacen_persistente.py

Fichas del catálogo en disco, formato JSON (mismo que el API). Un archivo por ficha: datos_locales/catalogo/espada_oxidada.json. Cada archivo guarda {"version": "v1.2", "datos": {...}}. Si la versión del servidor cambia, se descarta y re-descarga.

DecodificadorDatos — datos/decodificador_datos.py

Punto único de conversión JSON → objetos Python. No importa si el JSON viene del API o del disco, pasa por acá.

  • convertir_sala(datos): JSON → objeto Sala con Puertas
  • convertir_contenido(datos, fichas): JSON → Enemigos, ObjetoInstancia, Trampas vinculados a salas
  • aplicar_generales(estado, datos): configura cripta_id, sala_salida, llave_salida
  • aplicar_contenido(mapa, contenido): vincula enemigos/objetos/trampas a las salas del mapa

PlanificadorPrecarga — service/planificador_precarga.py

Usa BFS (Breadth-First Search) sobre el grafo de salas para decidir qué precargar.

Tamaño criptaEstrategia
≤20 salasCargar TODO de una vez
≤50 salasBFS profundidad 2 desde el jugador
50+ salasBFS profundidad 1 (solo vecinos)

Se adapta al presupuesto restante: >5 → agresivo, 2-5 → moderado, <2 → solo sala destino. Divide en chunks de 10 (límite del API).

PresupuestoSolicitudes — datos/presupuesto_solicitudes.py

Contador simple: lleva intentos vs límite. Lo usan el repositorio y el planificador para decidir si pueden pedir más datos o deben usar solo caché/disco.

4. Integrante 1 (Sofía) — Motor de Juego

Reglas del juego, simulación por turnos, combate y efectos temporales.

MotorJuego — logica/motor_juego.py

Motor central que valida y ejecuta todas las acciones del jugador. Implementa el contrato MotorJuegoContrato.

Acciones soportadas: MOVER, ATACAR, ABRIR, RECOGER, USAR, EQUIPAR, DESHACER, INSPECCIONAR, ESPERAR

Flujo de una acción:

  1. ejecutar_accion(accion) valida la acción según el tipo
  2. Registra la acción en el historial (para deshacer)
  3. Cobra el costo en tiempo (estado.reloj += costo)
  4. avanzar_hasta_decision() procesa eventos pendientes de la agenda hasta que el jugador deba actuar
  5. Activa enemigos de la sala y procesa trampas

Combate: el jugador ataca (daño = ataque_jugador - defensa_enemigo). Enemigos muertos sueltan botín preparado. Los enemigos responden según su comportamiento (guardián, patrulla).

MapaCripta — logica/mapa_cripta.py

Grafo de salas conectadas por puertas.

  • Almacenamiento interno: lista Python de objetos Sala (no dict, no TablaHash)
  • agregar_sala(sala): agrega al final de la lista
  • obtener_sala(id): búsqueda lineal O(n) por ID
  • obtener_salas(): retorna copia de la lista
  • vecinos_abiertos(sala): retorna salas accesibles por puertas abiertas
  • vincular_salidas(): resuelve los IDs de destino de las puertas a referencias reales de Sala

AgendaEventos — logica/agenda_eventos.py

Cola de prioridad para eventos futuros del juego (ataques de enemigos, efectos que vencen, trampas que se rearman).

  • Estructura principal: MontículoMínimo (min-heap) — el evento con menor tiempo está en la raíz
  • 3 índices AVL auxiliares: por ID, por prioridad (tiempo, secuencia), por destinatario
  • crear_evento(id, tiempo, secuencia, tipo, destinatario, datos): inserta en heap + 3 índices
  • extraer_siguiente(): saca el evento con menor tiempo, O(log n)
  • cancelar(id_evento): elimina un evento de todos los índices, O(log n)
  • Determinismo: la tupla (tiempo, secuencia) garantiza orden único incluso si dos eventos tienen el mismo tiempo

GestorEfectos — logica/gestor_efectos.py

Maneja efectos temporales sobre actores. Cada efecto es un dict con: id, tipo, objetivo (referencia al actor), valor, inicio, vencimiento, duración.

TipoQué haceEjemplo
VENENODaño periódico al objetivoTrampa de veneno
REGENERACIONCura periódica a un enemigoEnemigo con regen
ANTORCHAIlumina (solo una activa a la vez)Objeto antorcha
VELOCIDADCambia velocidad del actor temporalmentePoción de velocidad

Cada efecto programa eventos futuros en la agenda. Al vencer, se cancela automáticamente.

5. Integrante 3 (Joshua) — Controller, Vista, Inventario

Capa de presentación, orquestación del flujo de juego y estructuras de sesión.

ControladorJuego — controller/controlador_juego.py

REPL (Read-Eval-Print Loop) que parsea comandos de texto del jugador y los delega al servicio.

Comandos soportados: cripta, mover, atacar, abrir, recoger, usar, equipar, inventario, inspeccionar, deshacer, guardar, cargar, salir

Flujo:

  1. procesar_comando(texto) parsea el input
  2. Mapea a una Accion del dominio
  3. Delega a JuegoService.ejecutar_accion()
  4. Muestra resultado en la vista

Pendiente: cargar() lanza NotImplementedError porque falta reconstruir EstadoPartida completo desde el dict que retorna GuardadoBinario.cargar().

JuegoService — service/juego_service.py

Capa de orquestación entre el controller y el motor. No contiene lógica de juego propia.

  • iniciar_partida(estado): valida que el EstadoPartida tenga mapa, jugador, inventario, agenda, historial. Conecta todo y arranca el motor.
  • ejecutar_accion(accion): registra en log, delega al motor, retorna resultado.
  • conectar_inventario(inv): vincula el inventario al servicio.
  • Maneja replay de partidas (reproducción de logs) y registro de resultados.

Inventario — logica/inventario.py

Usa una ListaDobleImpl para almacenar objetos con un cursor que referencia el nodo seleccionado.

  • agregar(objeto): inserta al frente de la lista, selecciona el nuevo. Rechaza si está lleno. O(1).
  • siguiente() / anterior(): mueve el cursor al nodo vecino. O(1).
  • quitar_actual(): desconecta el nodo seleccionado, mueve cursor al vecino. O(1).
  • obtener_objetos(): recorre la lista y retorna una lista auxiliar (para ordenar sin modificar).
  • retirar_actual_con_registro(): retira el objeto y guarda un RetiroInventario para restaurarlo.
  • restaurar_retiro(registro): devuelve el nodo a su posición original usando marcas de orden.

Capacidad máxima viene de los datos de la cripta. Cada nodo tiene una _orden_inventario para reinsertar en la posición correcta durante deshacer.

HistorialReversible — logica/historial_reversible.py

Sistema de undo que almacena hasta 5 intervalos de cambios reversibles.

  • Estructura interna: ListaDobleImpl de TransaccionAccion (más reciente al frente)
  • Cada TransaccionAccion contiene una lista de CambioReversible
  • iniciar_intervalo(): abre un nuevo grupo de cambios
  • registrar(cambio): agrega un cambio al intervalo abierto
  • cerrar_intervalo(): finaliza el grupo
  • deshacer_ultimo(estado): saca el intervalo más reciente y revierte todos sus cambios en orden inverso
  • Límite de 5 intervalos: al insertar el sexto, descarta el más viejo

La lista doble permite insertar al frente y descartar del final en O(1).

6. Flujo de datos completo

Inicio de partida

  1. Controller recibe el comando cripta <id>
  2. JuegoService pide al ClienteAPI (o FuenteOffline) los generales de la cripta
  3. DecodificadorDatos aplica los generales al EstadoPartida (cripta_id, sala_salida, llave)
  4. ClienteAPI obtiene páginas de salas (esqueleto: IDs + puertas, paginado)
  5. DecodificadorDatos convierte cada página en objetos Sala → se agregan al MapaCripta
  6. PlanificadorPrecarga calcula qué salas precargar (BFS desde la sala inicial)
  7. RepositorioCatalogo resuelve fichas del catálogo: caché → disco → red
  8. DecodificadorDatos convierte contenido (enemigos, objetos, trampas) y lo aplica al mapa
  9. JuegoService conecta inventario, historial, agenda y arranca el motor

Durante la partida

  1. Controller parsea el comando del jugador
  2. JuegoService crea una Accion y la pasa al MotorJuego
  3. MotorJuego valida, ejecuta, registra en historial y cobra tiempo
  4. AgendaEventos procesa eventos pendientes (ataques enemigos, efectos que vencen)
  5. GestorEfectos aplica/cancela efectos temporales
  6. Vista muestra el resultado al jugador

Guardar partida

  1. Controller recibe guardar
  2. GuardadoBinario serializa: cabecera + jugador + extras v3 (inventario, efectos, stats, visitadas) + salas + índice
  3. Escritura atómica con archivo temporal + os.replace

Cargar partida (pendiente)

  1. GuardadoBinario.cargar() lee el archivo binario → retorna dict completo con todos los campos
  2. Controller (pendiente de Joshua) debe reconstruir EstadoPartida: crear Salas → MapaCripta, Jugador con sala_actual, Inventario con objetos, reconectar efectos por objetivo_id

Acceso directo a salas

El índice al final del archivo permite leer una sala sin cargar todo:

  1. Leer cabecera (62 bytes) → obtener offset_índice y num_salas
  2. Saltar al índice → buscar el offset de la sala deseada
  3. Saltar al offset → leer solo esa sala

Esto cumple el requisito del enunciado: "recuperar una sala específica sin leer el archivo completo".

Escritura atómica

Usa tempfile.mkstemp() + os.replace(): si falla la escritura a medio camino, el archivo anterior no se destruye. El índice va al final porque no se sabe el tamaño de cada sala hasta escribirla.
